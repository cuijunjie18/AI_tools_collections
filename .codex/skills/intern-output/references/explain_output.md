# 微信鸿蒙照片墙优化(白话版)

本身在微信实习，做客户端的大多数情况都是做一下业务，写一些UI、逻辑之类，在已有的框架上进行开发，没有那种从零到一的软件开发。所以我就讲一下我处理的一个微信线上P0的需求，当时被投诉反馈TOP8的问题，说一下我个人是如何分析思考并解决这个问题的。

鸿蒙有一个存储空间，支持用户清理聊天记录，有个照片墙，在加载用户可清理的媒体文件列表时，由于微信用户持有的媒体文件数量远超业界其他应用（数十万级别），导致 UI 线程长时间阻塞，触发 ANR（Application Not Responding），程序崩溃闪退。是当时最严重的P0问题之一(现网TOP8，大量用户反馈投诉)，也是我负责的第一个P0问题。

我是如何排查解决问题的？

我先把整个流程梳理了一遍，既然是UI线程发生的阻塞，那么就从UI入手，把整个调用链路梳理了一遍：

UI线程 <-> zidl桥接层 <-> c++层

目前的方案是：用户进入照片墙界面，应用层异步请求从c++层获取媒体文件列表。c++层将获取的数据500个一组，中间手动delay固定时间间隔，分批次发给应用层，应用层再进行UI渲染。

为什么要500个一组，不能直接全部回调？数据太多，回调到zidl桥接层的时候已经post到了UI线程，桥接层是负责做数据转换、传输的，需要把c++层传过来的数据(二进制Uint8数组)做转换(解码)，转换成对应的结构体，再传回给应用层，这一步是比较耗时的，如果一次性全部回调，那么zidl桥接层会阻塞UI线程，导致ANR。而zidl桥接层是不能做逻辑操作的，只能调用Uint82PbList这些数据转换操作，最后再把数据传给应用层。

## v1
- 先复现问题，本地测试机手动压测5w的图片，复现了问题
- 现网没有数据上报，先根据经验猜测最大数量，以微信聊天记录占1TB来说，每个媒体文件平均1mb，则需要支持100w的压测量(不过后来全量后加了数据上报发现全网最多的聊天文件目前是55w)。
- ANR问题，直接来看就是程序处理太慢，考虑算法层面的看能否优化，比如说降低时间复杂度之类的，在这一块做了一些优化，尽量把逻辑操作沉到c++，如排序操作等...发现优化了一点，但不多，可能阈值提高了1w~2w的图片
- 分析500个一组回调导致ANR的原因：鸿蒙的ArkTs是单线程语言(其实也支持多线程，这个后面我会讲到)，类似JS。而UI线程是以一个事件循环模型驱动task执行的，每个UI事件，回调函数都是相当于post一个task，然后加入到UI线程的looper里，因为c++回调事件的优先级高于UI task，如果回调太多、太快，会导致用户输入的UI事件饥饿，一直不被处理到，直到ANR。那提高c++层的回调间隔就显而易见，我们尝试把原本的5ms提高到50ms，发现20w数据量都没问题，但是再多还是会ANR，即单次回调在UI线程处理的时间一定是大于50ms的间隔的，后来排查根本原因还是跨语言调用太耗时，或者某些情况UI线程出现了其他耗时操作，导致整个回调处理过程可能会达到100ms级别，如果以这个为时间间隔，我们不能接受，UI加载太慢了。
- 上面就是第一版优化方案v1，本质是在c++层回调间隔中找到一个合适的值，使得Ui线程的消费速率接近c++层数据的产生速率，临时上线先解决部分用户的问题
- 上面的我个人觉得依旧不优雅，因为这种实现方式需要依赖主观因素，回调间隔，过小，容易导致ANR；过大，c++线程气泡现象明显，于是进入第二版v2的优化

## v2
- 分析第一版方案不够优雅和可以改进的原因：回调次数不固定、回调间隔主观定义、回调次数随着数据量大而增多，加重UI线程的压力
- 那么我就考虑了是不是可以消除多次回调，如果一次回调不就行了？而一开始我们就分析过一次回调不可行的原因：zidl桥接层仅做解码，解码太耗时(c++层传过来的数据需要解码出pb结构体，结构体很大，包含各种元数据，如缩率图路径、完整图片文件路径、该图片可清理的大小，媒体类型，uid等)，zidl桥接层又不能做逻辑操作的,没法进行其他操作。如果能够进行逻辑操作，我们就能在这里做一些类似c++层的分段操作，但在UI线程，分段与处理在同一个线程，能保证性能，不会产生不同线程因回调对齐而产生的气泡现象。那既然zidl桥接层没法进行逻辑操作，我干脆直接把c++层的二进制数据通过zidl桥接层透传会UI线程，即不在zidl桥接层做解码。这一关键步骤为v2版优化提供了可能性。
- c++原始数据回到UI线程后，如果在UI线程一下处理这么多数据，也依然会ANR。
- 于是我借鉴了之前分段回调的方式，只不过现在的分段回调并没有回调操作，只有分段，即把大量数据按原方案500次进行一次处理，处理完一段后，把下一段以处理以task的形式post到UI线程，UI线程消费task，继续处理下一段数据，如此循环，直到全部处理完毕。这样能保证UI事件与数据解码(业务逻辑)在同一个线程，优先级相同，不会出现UI事件一直没有被处理的情况，使得UI事件、业务逻辑处理按一定的事件循环顺序执行，根本上避免了ANR。其次这种方式保证了UI线程每次处理完一段数据才会处理下一段数据，不会出现需要手动设定一个固定时间间隔，导致UI线程出现空窗期(即既不处理业务逻辑、也不处理UI事件)，充分利用性能，保证UI界面加载速度
- 本地压测突破40w，较上个版本提升了100%。但是再往上就出现了OOM问题，这是新的瓶颈了

## v3
- 后续就一些OOM问题进行了解决，如路径前缀提取、压缩，时间换空间等优化，减少UI trace，手动更新UI等操作减少内存占用，压测极限到了80w
- 虽然没能达到预期的100w，但这套技术方案领导还是比较满意的，先上线了，后续再继续优化
- 上线后之前那些重度用户，一直投诉的用户，都给了我们很大的肯定，说解决了问题，后来我们的上报系统发现，现网最多的聊天文件数量是55w，还没到我们的极限，而更多的聊天文件数量受限于硬件设备的存储空间大小，用户进入这个照片墙清理界面就大概率是存储空间不足了，所以不用太担心55w这个现网极限值会快速提高
- 后来这套方案也拿了当月组里的最佳优化方案奖


## 多线程方案尝试

- 读到这里，你可能会问，虽然ArkTs是单UI线程的语言，但是实际上也支持多线程，为什么不用多线程呢？
- 这个问题问的好，ArkTs的多线程有以下几种方式实现，TaskPool、worker，我尝试过worker + SharedArray、worker + Sendable方案，均不可行
- 因为ArkTs的多线程不像c++/java这种多线程可以共享内存的语言，它的多线程到UI线程仍然需要数据传输(类似于解码)，而且限制大小，不太满足当前业务的要求
